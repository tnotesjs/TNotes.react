## 1. 【AI】`babel-plugin-react-compiler` 自动记忆化会有什么坑或者额外的成本吗？没有的话，新项目直接无脑上是不是就行了？

有坑、也有成本，但新项目大多可以「默认开」——不是完全无脑。

### 1.1. 可能的坑

1. **必须遵守 React 规则**：渲染期副作用、乱改 props/state、Hook 乱用等，Compiler 可能跳过优化，或行为怪异。应用 ESLint `eslint-plugin-react-hooks`（含 compiler 相关规则）一起上。
2. **不是 100% 组件都会被优化**：违规或分析不了的组件会被跳过（安全兜底），别假设「装了就全局自动最优」。
3. **和手写 memo 语义叠在一起**：旧代码里的 `useMemo`/`useCallback` 一般可留着；乱删可能改变行为。新代码可以少写，但不是「删光才正确」。
4. **Effect 依赖等边界**：有时你仍要用 `useMemo`/`useCallback` 精确控制「这个值别变，否则 Effect 狂跑」。Compiler 是启发式，细控时仍可能需要手写。
5. **调试心智**：重渲染变少后，出问题要靠 DevTools（✨ Memo）或编译产物排查，比纯手写稍抽象一点。

### 1.2. 额外成本

| 成本 | 说明 |
| --- | --- |
| 构建 | 多一道编译，一般可接受，大仓会更明显 |
| 配置 | Vite/Babel 要接插件，版本要对齐 |
| 学习 | 团队要懂「规则 + 何时 opt-out（`use no memo`）」 |

### 1.3. 新项目要不要无脑上？

**可以默认开**，尤其是 React 19 + Vite/Next 新项目，官方也鼓励试。

更稳妥的做法：

1. 开 Compiler
2. 配好 `eslint-plugin-react-hooks`
3. 用 DevTools 抽查关键路径
4. 出问题的组件再 `use no memo` 或局部手写记忆化

**不必无脑的情况**：极小玩具页、构建链很怪/难接插件、团队还不熟 React 规则——先把规则跑顺再开也行。

一句话：新项目「默认上」合理；「无脑」要改成「开着 + ESLint + 出问题再兜底」。

## 2. 【AI】手写记忆化虽然样板代码多，但是更加直观可控，能减少魔法，对吗？

大体对，可以这么理解。

手写 `memo` / `useMemo` / `useCallback`：

+ **更直观**：优化意图写在源码里，读代码就能看到「这里故意稳住引用 / 跳过渲染」
+ **更可控**：依赖数组、比较范围由你定，Effect 依赖、传给子组件的引用也能精确卡
+ **少一层构建魔法**：不依赖编译器插桩，行为更接近「你写什么就是什么」

但要注意：手写也不是零魔法。依赖漏写、浅比较、内联箭头毁掉 `memo`（0016）同样隐蔽，只是魔法在「人脑 + Hook 规则」里，不在编译器里。

所以更准确的说法是：手写记忆化样板多，但优化边界更显式、更好推理；Compiler 省样板，把决策交给构建期启发式。新项目可默认 Compiler；需要精确控制或排查问题时，手写（或 `use no memo`）仍然有价值。
